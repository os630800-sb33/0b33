================================================================================
KEY FINDINGS
================================================================================

Finding 1: Nested Sub-Accounts NOT SUPPORTED (By Design)
  Status: ✅ Confirmed
  Evidence: Code review of Subscription type, API surface, charge routing
  Impact: Non-breaking architectural decision
  Details:
  - Subscription.sub_account_label: Option<Symbol> (single label, no parent)
  - register_sub_account(merchant, label) API (no nesting parameters)
  - Storage key: (merchant, label) tuple (flat lookup, no recursion)

Finding 2: Fee Applied EXACTLY ONCE Per Charge
  Status: ✅ Verified by test suite
  Evidence: fee_applied_once_to_sub_account_charge test
  Formula: fee = max(gross × fee_bps / 10_000, 1)
  No Double-Application: Computed at subscription charge time, before routing

Finding 3: CONSERVATION INVARIANT Holds Universally
  Status: ✅ Verified by 11+ test cases
  Invariant: net + fee == gross
  Evidence: Multiple test scenarios across two test files
  Applies to: All charge types, all sub-account scenarios, edge cases

Finding 4: NO Double-Charging Risk
  Status: ✅ Confirmed by atomicity analysis
  Evidence: no_double_charging_single_level_routing test
  Details:
  - Prepaid deducted exactly once per charge
  - Fee computed exactly once at charge time
  - Sub-account credited exactly once
  - Reentrancy guards in place

Finding 5: DUST Protection (Minimum-Fee Floor)
  Status: ✅ Verified
  Evidence: minimum_fee_floor_applied_to_sub_account test
  Details:
  - 1-unit minimum fee when fee_bps > 0 and treasury configured
  - Prevents protocol fee leakage on micro-charges
  - Example: 1-unit charge at 2.5% → treasury receives 1 unit (floor)

Finding 6: SUB-ACCOUNT Isolation Confirmed
  Status: ✅ Verified
  Evidence: Unique storage key per (merchant, label) tuple
  Details:
  - Independent balances per sub-account
  - Independent balances per token
  - No cross-contamination between sub-accounts
